```
                        │  (企业微信/邮件/系统)   │
                        └──────────────────────┘
```

> 与车险监控的关键差异：
> - 链鉴 AML **不产生自动处置决策**（不冻结、不拒绝、不报送），预警的"业务结果"通过**人工审核反馈**回流，人工确认/驳回即天然延迟标签。
> - AMLSim **测试标签不参与线上推理，仅用于离线评估**，因此线上性能靠人工反馈，月报性能靠离线评估。
> - 新增三个监控维度：**规则引擎命中**、**资金图谱结构**、**LLM Agent 质量**。

### 2.1 客群稳定性 PSI（账户/交易特征）

监控反洗钱特征在线上与训练/基准集之间的分布偏移。PSI 越高，说明进入系统的交易或账户结构发生了改变，可能意味着洗钱模式变化或数据口径变更。

**交易场景计算示例（"单笔交易金额"特征）：**

| 交易金额分档 | 基准占比（训练集） | 当前线上占比 | 变化 | PSI 分量 |
|------------|-----------------|------------|------|---------|
| 0-1 万 | 40% | 32% | -8% | 0.018 |
| 1-10 万 | 35% | 34% | -1% | 0.000 |
| 10-50 万 | 15% | 22% | +7% | 0.028 |
| 50-100 万 | 7% | 9% | +2% | 0.004 |
| 100 万以上 | 3% | 3% | 0% | 0.000 |
| **合计** | **100%** | **100%** | — | **PSI=0.050** |

> 上例 PSI=0.05 → 🟢 稳定

**账户场景计算示例（"账户交易频率"特征）：**

| 频率分档（笔/日） | 基准占比 | 当前线上占比 | 变化 | PSI 分量 |
|----------------|---------|------------|------|---------|
| 0-5 | 55% | 42% | -13% | 0.039 |
| 5-20 | 30% | 33% | +3% | 0.003 |
| 20-50 | 10% | 17% | +7% | 0.039 |
| 50-200 | 4% | 7% | +3% | 0.016 |
| 200 以上 | 1% | 1% | 0% | 0.000 |
| **合计** | **100%** | **100%** | — | **PSI=0.097** |

> 上例 PSI=0.097 → 🟢 稳定（但接近轻微偏移，需关注高频账户增多，疑似拆分转账活跃）

#### 阈值与告警

| 等级 | PSI 范围 | 标色 | 含义 | 对应动作 |
|------|---------|------|------|---------|
| 🟢 稳定 | PSI < 0.10 | 绿色 | 交易/账户客群结构稳定，模型可信任 | 正常监控，无需处理 |
| 🟡 轻微偏移 | 0.10 ≤ PSI < 0.25 | 黄色 | 客群发生轻度变化，但幅度可控 | 排查偏移方向，持续观察 3 个监控周期 |
| 🔴 严重漂移 | PSI ≥ 0.25 | 红色 | 交易/账户结构发生根本性改变 | **立即暂停预警参考**，启动全面排查 |

#### 反洗钱场景实际解读

**场景一：PSI 持续上升至 0.18 — 交易金额档位右移（黄色预警）**

```
日报表现：
  ┌─────────────────────────────────────────────┐
  │ 日期       │ PSI    │ Top-1 偏移特征        │
  ├─────────────┼────────┼───────────────────────┤
  │ 07-28 (基准)│ —     │ —                    │
  │ 07-29        │ 0.04  │ 正常                 │
  │ 07-30        │ 0.09  │ 正常                 │
  │ 07-31        │ 0.13  │ → 10-50万档交易增加   │
  │ 08-01        │ 0.18  │ → 10-50万档交易增加   │
  └─────────────────────────────────────────────┘
```

**合规人员看到的实际影响**：
- 10-50 万元档位的交易占比从 15% → 22%
- 该档位正是"拆分转账"规避大额监测的常用区间，可能意味着新型拆分模式

**排查思路**：

| 排查步骤 | 做什么 | 数据来源 | 预期结论 |
|---------|-------|---------|---------|
| ① 定位偏移特征 | 逐一计算每个特征的 PSI 贡献度，找 Top-3 | 监控系统 PSI 明细表 | 确定是"交易金额"还是"账户频率"等在变 |
| ② 结合规则命中明细 | 查看当日拆分转账/多跳归集规则命中是否同步上升 | 规则命中明细表 | 判断偏移是否为真实洗钱行为，而非数据变化 |
| ③ 溯源数据导入 | 检查上游 CSV 是否有新渠道/新账户类型涌入 | 数据导入记录 | 是否导入口径变化（如新增对公账户数据） |
| ④ 检查规则参数 | 确认规则阈值、评分权重是否被修改 | 规则配置审计 | 规则调整导致打分类别变化 |

**解决方案**：

| 问题根因 | 解决方案 | 执行方 | 时效 |
|---------|---------|-------|------|
| 新增数据源/账户类型（如对公账户） | ① 单独评估该类型账户风险；② 更新基准分布 | 甲方数据 + 乙方 | 3 天 |
| 真实拆分模式变化 | ① 标记观察；② 若 PSI 持续抬升，启动规则/特征迭代 | 乙方 | 2-4 周 |
| 规则参数被调整 | 回滚配置，规范变更流程 | 系统管理员 | 即时 |
| 模型训练客群偏差 | 重新采样训练数据，扩充异常样本 | 乙方 | 2 周 |

**场景二：PSI 突然跳升至 0.36 — 账户频率分档骤变（红色告警）**

```
日报表现：
  07-30 PSI=0.06（正常）
  07-31 PSI=0.36（🔴 红色告警 → 20-200笔/日档位骤增）
```

**紧急排查重点**：
- **优先排查数据导入**：是否导入了异常批次的交易（如重复导入、刷单数据）
- **其次排查规则参数**：拆分转账/异常高频规则阈值是否被误改
- **最后排查真实行为**：是否出现了新的高频交易团伙（结合图谱连通分量验证）

**紧急处置流程**（红色告警时）：

```
        红色告警触发
            │
            ▼
   ╔════════════════════════╗
   ║ 步骤1：确认数据导入正常 ║ ← 检查 CSV 是否重复导入/字段取值错误
   ╚════════════════════════╝
            │
            ▼
   ╔════════════════════════╗
   ║ 步骤2：切换至保守策略   ║ ← 预警暂缓自动生成，高风险预警强制人工审核
   ╚════════════════════════╝
            │
            ▼
   ╔════════════════════════╗
   ║ 步骤3：通知相关干系人   ║ ← 合规负责人、技术负责人
   ╚════════════════════════╝
            │
            ▼
   ╔════════════════════════╗
   ║ 步骤4：乙方排查分析     ║ ← 2 小时内输出排查报告
   ╚════════════════════════╝
```

### 2.2 特征分位数监控（交易金额 / 账户交易量）

监控反洗钱关键特征的**极端值分布**是否发生突变。在反洗钱场景中，极端值往往比均值更危险。

| 分位数 | 单笔交易金额含义 | 账户日累计交易含义 |
|--------|----------------|------------------|
| **P10** | 小额交易的分界线（占比最大的普通交易） | 低活跃账户的分界线 |
| **P90** | 大额交易分界线 | 高活跃账户分界线 |
| **P95** | 明显大额交易 | 疑似"洗钱通道账户"分界线 |
| **P99** | 全平台最极端的大额交易 | 高度疑似批量转账/归集账户 |

**反洗钱重点关注特征**：
- 交易侧：单笔交易金额、账户日累计交易金额、账户近 7 天累计交易笔数、单账户单日交易对手数
- 账户侧：账户余额、开户时长、历史累计流入/流出金额

#### 阈值与告警

| 分位数 | 波动幅度 | 告警级别 | 含义 |
|--------|---------|---------|------|
| P10 | > 30% | 🟡 黄色 | 小额交易结构变化 |
| P90/P95 | > 40% | 🟡 黄色 | 大额交易结构变化 |
| **P99** | **> 50%** | **🔴 红色** | **极端大额/高频交易涌入，高危** |
| 任何分位数 | > 20% 且连续 3 天趋势 | 🟡 黄色 | 持续性偏移，需关注 |

#### 反洗钱场景实际解读

**场景：单笔交易金额 P99 飙升 62%（红色告警）**

```
日报表现：
  ┌─────────────────────────────────────────────┐
  │ 特征：单笔交易金额（Transaction Amount）     │
  ├─────────────┬──────────┬──────────┬─────────┤
  │ 分位数      │ 基准值    │ 当前值    │ 变化幅度 │
  ├─────────────┼──────────┼──────────┼─────────┤
  │ P10        │ 0.3 万   │ 0.28 万  │ -7%  🟢 │
  │ P50        │ 3.5 万   │ 3.8 万   │ +9%  🟢 │
  │ P90        │ 42 万    │ 55 万    │ +31% 🟡 │
  │ P95        │ 90 万    │ 128 万   │ +42% 🟡 │
  │ P99        │ 220 万   │ 356 万   │ +62% 🔴 │
  └─────────────┴──────────┴──────────┴─────────┘
```

**合规人员看到的实际影响**：
- P99 飙升 → 最极端的 1% 交易金额门槛从 220 万抬到 356 万
- 这批超大额交易可能涉及：大额拆入资金、多跳归集的尾端落账、或正常对公大额结算
- **风险**：若规则阈值未同步调整，这批交易可能因"单笔未超监测阈值"而漏报

**排查思路**：

| 步骤 | 操作 | 说明 |
|------|------|------|
| ① | 筛选 P99 以上的交易清单 | 看这些交易的付款方/收款方、交易类型、时间段分布 |
| ② | 查这些账户在图谱中的位置 | 是否处于多跳归集/循环交易链路的末端 |
| ③ | 检查模型的预警命中 | 规则/评分有没有给这批交易正确打标 |
| ④ | 查看人工审核结果 | 是否因预警漏报而未被审核 |

**解决方案**：

| 排查发现 | 可能根因 | 处理方案 |
|---------|---------|---------|
| P99 以上交易集中在少数对公账户 | 正常大额对公结算（如货款） | 单独评估该账户类型，设置独立监测阈值 |
| P99 以上交易呈现"多进一出"模式 | 多跳归集/资金池 | 启动专项调查，确认团伙名单，扩充可疑标签 |
| 交易数量也同步大增 | 极端样本变多（金额大且笔数多） | 分析画像，考虑扩充训练集、新增规则 |
| 数据与规则排查均无异常 | 周期性波动（如季末资金归集） | 确认历史同期波动，正常监控 |

### 2.3 特征缺失率波动（导入字段）

监控**每一个反洗钱特征**在线上使用时的缺失率，与基准缺失率对比。缺失率突变是**上游数据导入问题**的最直接信号。

#### 阈值与告警

| 变化幅度 | 告警级别 | 含义 |
|---------|---------|------|
| 缺失率与基准偏差 ≤ 5% | 🟢 正常 | 数据源稳定 |
| 缺失率与基准偏差 5%-10% | 🟡 黄色预警 | 注意观察，可能是偶发问题 |
| **缺失率与基准偏差 > 10%** | **🔴 红色告警** | **大概率上游 CSV/接口故障** |
| 某个特征突然从 0% 变 100% 缺失 | 🔴 紧急告警 | 数据源彻底断连 |

#### 反洗钱场景实际解读

**场景：交易时间字段缺失率从 0% 飙升至 42%**

```
日报表现：
  ┌──────────────────────────────────────────────────────┐
  │ 特征名称            │ 基准缺失率 │ 当前缺失率 │ 变化  │ 告警 │
  ├──────────────────────┼───────────┼───────────┼───────┼─────┤
  │ 交易时间             │ 0.0%      │ 42.3%     │ +42%  │ 🔴  │
  │ 付款方账户ID         │ 0.0%      │ 38.6%     │ +39%  │ 🔴  │
  │ 交易金额             │ 0.0%      │ 0.1%      │ +0.1% │ 🟢  │
  │ 收款方账户ID         │ 0.5%      │ 0.8%      │ +0.3% │ 🟢  │
  │ 交易类型             │ 1.2%      │ 1.5%      │ +0.3% │ 🟢  │
  └──────────────────────────────────────────────────────┘
```

**合规人员看到的实际影响**：
- 交易时间/付款方缺失 → 这笔交易无法关联到账户和时间线
- 依赖时间特征的规则（拆分转账的"短时间"、异常高频的"频率"）全部失效
- 图谱构建中缺失付款方 → 边的起点缺失，资金链路断裂
- **后果**：检测结果严重失真，且不可追溯（违反 PRD 的"可追溯、可解释"要求）

**排查思路与解决流程**：

```
发现缺失率飙升（交易时间 0%→42%）
            │
            ▼
   ┌───────────────────────────────────────────────┐
   │ ① 确认是全线上升还是局部上升                    │
   │    - 所有交易都缺失？→ 导入脚本/CSV 映射全局故障 │
   │    - 某批次/某 CSV 文件集中缺失？→ 该文件解析错误 │
   └───────────────────────────────────────────────┘
            │
            ▼
   ┌───────────────────────────────────────────────┐
   │ ② 检查导入链路                                 │
   │    - CSV 表头是否变更（列名/列顺序）            │
   │    - 字段映射配置是否被改动                     │
   │    - 新增数据源字段口径不一致                   │
   └───────────────────────────────────────────────┘
            │
            ▼
   ┌───────────────────────────────────────────────┐
   │ ③ 系统侧临时处置                               │
   │    - 缺失交易标记"待补全"，不参与规则/图谱计算   │
   │    - 或暂停该批次导入，回滚至上一批次            │
   └───────────────────────────────────────────────┘
```

**常见根因与解决方案对照表**：

| 现象 | 根因 | 解决 | 责任方 |
|------|------|------|-------|
| 单个字段缺失率突增 | CSV 该列解析失败/映射错误 | 修复字段映射，重跑导入 | 乙方 |
| 多个字段同时缺失 | 数据源断连/表头整体变更 | 检查导入脚本与上游格式 | 甲方数据 + 乙方 |
| 新增数据源字段缺失 | 新数据源口径不一致 | 统一字段标准，缺失值补策略 | 甲方数据管理 |
| 缺失率正常但值全为默认值 | 上游返回默认值而非真实值 | 检查数据生成/清洗逻辑 | 乙方 |

### 2.4 风险评分 PSI（无标签前置预警）

在**还没有人工审核反馈**（即还不知道预警是否真可疑）的情况下，通过模型输出的风险评分分布变化，提前发现打分行为偏移。**这是最核心的前置预警指标**——它综合反映数据、规则、图谱、参数所有变化的最终影响。

#### 阈值与告警

| 等级 | 风险评分 PSI | 含义 | 影响预估 |
|------|------------|------|---------|
| 🟢 | < 0.10 | 模型打分稳定 | 预警量与风险等级分布与基准基本一致 |
| 🟡 | 0.10 - 0.25 | 打分轻度偏移 | 预警量可能波动 5-15%，需关注 |
| 🔴 | ≥ 0.25 | 打分严重漂移 | 预警量骤升/骤降，检测结果失真 |

#### 反洗钱场景实际解读

**场景一：风险分整体右移（风险评分 PSI=0.31，红色告警，预警量暴增）**

```
训练时风险分分布（基准）：
  ■■■■■■■■■■■■■■■■■■■■■■■■ 0-20 分（低风险 45%）
  ■■■■■■■■■■■■■■■■ 20-40（中低 30%）
  ■■■■■■■■■■ 40-60（中风险 15%）
  ■■■■ 60-80（中高 7%）
  ■■ 80-100（高风险 3%）

当前线上风险分分布：
  ■■■■■■ 0-20 分（低风险 12%） ↓↓↓
  ■■■■■■■■■ 20-40（中低 18%） ↓↓
  ■■■■■■■■■■■■■■■ 40-60（中风险 28%） ↑↑
  ■■■■■■■■■■■■■■■■■■■ 60-80（中高 34%） ↑↑↑
  ■■■■■■ 80-100（高风险 8%） ↑↑
```

**合规人员看到的实际影响**：
- 高分段（60 分以上）占比从 10% 暴增到 42%
- **预警量可能成倍增加**，人工审核积压 → 平均审核时长上升
- 若为真实风险上行（如新洗钱团伙涌入），是正确报警；若为误报，则审核资源被浪费

**排查方向**（优先级从高到低）：

| 优先级 | 排查方向 | 具体操作 |
|-------|---------|---------|
| 🔴 最高 | 数据源是否正常 | 检查缺失率（见 2.3），缺失填充导致默认高分 |
| 🔴 最高 | 特征分布是否突变 | 计算各特征 PSI（见 2.1），找导致漂移的关键特征 |
| 🔴 最高 | 规则/图谱是否变化 | 规则参数是否调整；图谱是否扩大（新增边导致关联度上升） |
| 🟡 中 | 是否上线了新模型版本 | 确认评分逻辑/权重配置是否被误替换 |
| 🟡 中 | 外部环境是否变化 | 新增了高风险数据源或大额交易批量涌入 |

**解决方案**：

| 根因 | 方案 | 执行周期 |
|------|------|---------|
| 数据缺失导致默认填充为高分 | 修复数据源或调整填充策略 | 即时修复 |
| 图谱扩大导致关联度普遍上升 | 复核边/路径阈值，必要时回滚图谱构建版本 | 1-3 天 |
| 规则参数被误放宽 | 回滚配置 | 即时修复 |
| 真实风险上行（新团伙） | 专项调查，确认后扩充样本、更新基准 | 2-4 周 |

**场景二：风险分整体左移（风险评分 PSI=0.29）**

```
当前线上风险分分布：
  ■■■■■■■■■■■■■■■■■■■■■■■■■■■■ 0-20 分（低风险 62%）↑↑↑
  ■■■■■■■■■■■■ 20-40（中低 24%）↓
  ■■■■■ 40-60（中风险 8%）↓↓
  ■■ 60-80（中高 4%）↓
  ■ 80-100（高风险 2%）↓
```

**合规人员看到的实际影响**：
- 看起来"交易变干净了"？预警量骤降，审核人员"轻松了"
- **实际上更危险**：模型可能把可疑账户也打成了低分，漏报
- **后果**：洗钱行为悄悄通过，无人审核，事后难追溯

**注意**：分数整体左移（全部变低分）往往比右移更危险，因为：
- 右移 → 预警量暴增 → 审核人员立刻发现并反馈（大声报警）
- 左移 → 预警量骤降 → 看起来"一切太平" → **漏报后置暴露**（沉默杀手）

**解决方案**：
- 左移场景必须**立即排查规则/图谱/评分是否失效**（是否被误关闭、图谱边丢失、标签误入训练）
- 检查是否漏建了关键边（如付款方字段缺失导致路径断裂）
- 分析是哪个特征/规则的变化导致分数整体偏低

### 2.5 线上性能指标（Precision/Recall/F1）

在积累足够的**真实标签**后，计算模型的真实检测能力。这是**最终验证**指标。

**链鉴 AML 的标签来源**（与车险不同）：
- **线上（周/月）**：人工审核结果作为延迟标签 —— 审核员"确认风险"的预警 ≈ 正样本（真阳性），"驳回"的预警 ≈ 负样本（假阳性）
- **离线（月，对照评估）**：AMLSim 已知可疑账户/交易标签 —— **仅用于离线评估，绝不参与线上推理**，用来计算 Precision/Recall/F1、PR-AUC、Precision@20/50

#### 阈值与告警

| 指标 | 基准（训练/测试时） | 告警阈值 | 告警级别 | 含义 |
|------|------------------|---------|---------|------|
| **预警确认率**（≈精确率代理） | 假设 78% | 线上 < 60% | 🔴 红色 | 预警中假阳性过多，审核资源被浪费 |
| | | 线上 < 70% 且持续下降 | 🟡 黄色 | 预警质量下降趋势 |
| **可疑账户召回率**（离线） | 假设 82% | 线上 < 70% | 🔴 红色 | 漏报大量可疑账户 |
| | | 线上 < 76% 且下降 > 3% | 🟡 黄色 | 漏报趋势需关注 |
| **Precision@20**（离线） | 假设 0.85 | 线上 < 0.65 | 🔴 红色 | 高风险排序 Top 中混入过多正常账户 |
| **F1**（离线） | 假设 0.75 | 线上 < 0.60 | 🔴 红色 | 整体检测性能失衡 |

> 离线评估方法见 PRD 11.1（检测效果）与 11.2（链路定位效果）。

#### 实际场景解读

**场景：上线第 3 个月，人工确认率从 78% 跌至 52%**

```
月报表现：
  ┌─────────────────────────────────────────────────┐
  │ 月份       │ 预警数  │ 确认率 │ 驳回率 │ 可疑账户召回 │
  ├─────────────┼────────┼───────┼───────┼───────────┤
  │ 测试集      │ —      │ —     │ —     │ 84%       │
  │ 上线第 1 月 │ 9,200  │ 78%   │ 15%   │ 81%       │
  │ 上线第 2 月 │ 10,100 │ 71%   │ 20%   │ 76%       │
  │ 上线第 3 月 │ 12,600 │ 52%   │ 38%   │ 68%       │
  └─────────────────────────────────────────────────┘
```

**合规人员看到的实际影响**：
- 预警量从 9,200 涨到 12,600（看起来"能力变强"）
- 确认率从 78% 掉到 52% → **一半以上预警是误报**
- 可疑账户召回从 81% 掉到 68% → 真正的可疑账户在漏报
- **结论**：模型正在失效，假阳性膨胀，真阳性漏报

**排查与解决流程**：

```
【前置排查】— 先看前置指标（PSI、缺失率、分位数、规则命中）
  ┌──────────────────────────────┐
  │ 前置指标是否已告警？          │
  │ YES → 根因已在前置环节定位    │
  │ NO  → 性能衰减是渐进式（自然老化）│
  └──────────────────────────────┘
            │
            ▼
【根因诊断】— 定位假阳性来源
  ① 拆分假阳性预警：按规则类型切分确认率，找出"高命中低确认"的规则
  ② 分析假阳性账户画像：新账户/对公账户/特定地区？
  ③ 检查是否规则参数过松或图谱误连边
            │
            ▼
【决策】
  ┌─────────────────────────────────────────────┐
  │ 确认率下降程度           │ 建议操作           │
  ├──────────────────────────┼───────────────────┤
  │ 确认率 70%-78%           │ 持续监控，1 月后复查 │
  │ 确认率 60%-70%           │ 准备训练数据，启动迭代 │
  │ 确认率 < 60%             │ 立即收紧规则参数/切换备用模型 │
  └─────────────────────────────┴───────────────────┘
```

### 2.6 规则引擎命中监控

反洗钱系统以**规则引擎**为检测主力（首期 6 条规则），规则命中量是检测行为的直接体现。规则命中异常往往早于评分 PSI 出现。

**6 条首期规则**：拆分转账、循环交易、多跳归集、异常高频转账、异常金额波动、高风险关联（详见 PRD 8.2）。

#### 监控内容与阈值

| 指标 | 正常范围 | 告警级别 | 含义 |
|------|---------|---------|------|
| 单规则命中量环比波动 | ≤ ±30% | 🟢 正常 | 规则行为稳定 |
| 单规则命中量环比波动 30%-80% | | 🟡 黄色 | 规则行为变化，需定位原因 |
| **单规则命中量环比波动 > 80%** | | **🔴 红色** | 规则失效/参数变更/真实异常涌入 |
| 某规则连续 7 天命中量 < 基准 20% | | 🟡 黄色 | 规则疑似被绕过或参数失效 |
| 规则参数/阈值被修改 | 必须走变更流程 | 🔴 红色（未报备） | 配置审计异常 |

#### 反洗钱场景实际解读

**场景一：循环交易规则命中从 20 笔/日 骤增至 480 笔/日（红色告警）**

```
日报表现：
  ┌─────────────────────────────────────────────┐
  │ 规则            │ 07-28 │ 07-29 │ 07-30 │ 07-31 │
  ├─────────────────┼───────┼───────┼───────┼───────┤
  │ 拆分转账         │ 412   │ 418   │ 425   │ 430   │
  │ 循环交易         │ 20    │ 26    │ 175   │ 480 🔴│
  │ 多跳归集         │ 386   │ 391   │ 388   │ 395   │
  │ 异常高频转账     │ 214   │ 220   │ 219   │ 225   │
  │ 异常金额波动     │ 134   │ 138   │ 141   │ 139   │
  │ 高风险关联       │ 182   │ 185   │ 180   │ 188   │
  └─────────────────────────────────────────────┘
```

**排查思路**：

| 步骤 | 操作 | 说明 |
|------|------|------|
| ① 检查参数配置 | 循环交易的"回到原账户/关联账户"的跳数、时间窗口是否被调整 | 配置审计日志 |
| ② 检查上游数据 | 是否新增了特定类型交易（如 A 转 B 转 A 的对敲交易） | 交易明细 |
| ③ 检查图谱构建 | 边/路径计算是否异常（如把普通转账误判为循环） | 图谱构建日志 |
| ④ 抽验命中样本 | 人工抽查 20 条命中交易是否真的构成循环 | 人工复核 |

**场景二：异常金额波动规则连续 10 天命中为 0（黄色预警）**

- 可能原因：规则参数被误改（波动阈值设得过大）、该特征缺失率高导致无法计算、规则逻辑 bug
- **处置**：检查规则状态与参数 → 若无异常，则该规则可能已被新型交易模式绕过 → 标记观察并准备迭代

### 2.7 资金图谱结构监控

资金图谱（账户=节点、交易=边）是链鉴 AML 的核心分析对象。图谱结构异常往往对应团伙聚集、大规模资金归集等洗钱信号，也会直接影响评分（路径复杂度占 20%）。

#### 监控内容与阈值

| 指标 | 正常范围 | 告警级别 | 含义 |
|------|---------|---------|------|
| 图规模（节点数/边数） | 环比 ≤ ±20% | 🟢 | 图谱规模稳定 |
| 节点/边数环比 > 50% | | 🟡 | 数据量突变，检查导入 |
| **最大连通分量大小** | 环比 ≤ ±30% | 🟢 | 网络结构稳定 |
| 最大连通分量突然翻倍 | | **🔴** | 大规模资金归集网络形成 |
| 高连通账户数（单账户对手 ≥ 20） | 环比 ≤ ±30% | 🟢 | — |
| 高连通账户数异常上升 | | 🟡 | 疑似"通道账户"聚集 |
| 1-3 跳路径数量 | 环比 ≤ ±50% | 🟢 | 关联路径稳定 |
| 图谱查询平均耗时（P99） | < 500ms | 🟢 | 查询性能达标 |
| 图谱查询耗时突增 | P99 > 1s | 🟡 | 图规模过大/索引失效 |

#### 反洗钱场景实际解读

**场景：最大连通分量从 180 个账户膨胀到 1,240 个账户（红色告警）**

**合规人员看到的实际影响**：
- 一个包含 1,200+ 账户、可能存在多跳归集的巨型网络突然成型
- 若为真实团伙，这正是"多跳归集"的高危信号，应启动专项调查
- 但也要排除数据误连边（如共享收付款账户字段错误）导致的虚假关联

**排查思路**：

| 步骤 | 操作 | 说明 |
|------|------|------|
| ① 检查新连边来源 | 定位新增边对应的交易，看是否真实 | 交易明细 |
| ② 抽验关键中间节点 | 挑 5-10 个"桥接账户"，验证其交易真实性 | 人工复核 |
| ③ 检查数据导入 | 是否重复导入或字段错位（付款方/收款方颠倒） | 导入日志 |
| ④ 判定性质 | 真实团伙 → 专项调查；数据问题 → 修复重构图谱 | 结论归档 |

### 2.8 LLM Agent 质量与推理资源监控

链鉴 AML 的 **Agent（智能调查）与报告生成依赖昇腾 NPU 部署的大模型**。这是车险监控中没有的维度，LLM 的不可靠性是最大的新增风险源。

#### 2.8.1 Agent 质量指标

| 指标 | 正常范围 | 告警级别 | 含义 |
|------|---------|---------|------|
| 工具调用成功率（图谱查询/交易检索/规则解释/安全计算） | ≥ 99% | 🟢 | 工具链路正常 |
| 工具调用成功率 < 95% | | 🟡 | 下游服务故障，回答可靠性下降 |
| **工具调用成功率 < 90%** | | **🔴** | 图谱/交易服务严重故障，Agent 不可用 |
| 报告生成成功率 | ≥ 98% | 🟢 | 报告链路正常 |
| 单条预警分析平均耗时 | ≤ 30s（含推理） | 🟢 | 响应达标 |
| 单份报告生成平均耗时 | ≤ 60s | 🟢 | 响应达标 |

#### 2.8.2 LLM 输出质量（每日抽评 + 周汇总）

| 指标 | 正常范围 | 告警级别 | 含义 |
|------|---------|---------|------|
| **幻觉率**（引用了不存在的交易/账户/规则） | ≤ 2% | 🟢 | 输出可信 |
| 幻觉率 2%-5% | | 🟡 | 关注，核查触发幻觉的场景 |
| **幻觉率 > 5%** | | **🔴** | 暂停自动报告，强制人工复核 |
| 证据正确率 | ≥ 95% | 🟢 | 引用的证据真实可追溯 |
| 规则解释正确率 | ≥ 95% | 🟢 | 规则解释准确 |
| 报告完整率 / 可审核率 | ≥ 90% | 🟢 | 报告可直接人工审核 |

> 抽评口径见 PRD 11.3：随机抽取至少 30 个预警，由人工评估证据正确率、规则解释正确率、报告完整率、报告可审核率、幻觉率。

#### 2.8.3 昇腾 NPU 资源指标

| 指标 | 正常范围 | 告警级别 | 含义 |
|------|---------|---------|------|
| 推理成功率 | ≥ 99% | 🟢 | 昇腾环境稳定 |
| 推理成功率 < 95% | | 🟡 | 环境异常，检查资源 |
| **推理成功率 < 90%** | | **🔴** | NPU 故障/显存不足，服务降级 |
| 平均推理时长 | ≤ 15s | 🟢 | 响应达标 |
| NPU 利用率 | 峰值 ≤ 90% | 🟢 | 资源充足 |
| NPU 利用率持续 100% | | 🟡 | 资源紧张，需扩容 |

#### 反洗钱场景实际解读

**场景：幻觉率抽评升至 6.5%（红色告警）**

```
周报表现：
  ┌─────────────────────────────────────────────┐
  │ 周次    │ 抽评预警数 │ 幻觉率 │ 证据正确率 │ 触发场景 │
  ├──────────┼──────────┼───────┼───────────┼─────────┤
  │ 第 1 周  │ 35       │ 0%    │ 100%      │ —       │
  │ 第 2 周  │ 32       │ 0%    │ 100%      │ —       │
  │ 第 3 周  │ 36       │ 3.1%  │ 97%       │ 长路径查询 │
  │ 第 4 周  │ 33       │ 6.5%  │ 92%       │ 长路径查询 │
  └─────────────────────────────────────────────┘
```

**合规人员看到的实际影响**：
- 报告中开始出现"不存在的交易""虚构的资金路径"
- 审核员若直接采信，会形成错误调查结论
- 幻觉集中在"长路径查询"场景 → 工具返回路径太长，LLM 上下文截断后自行补全

**排查思路与处置**：

| 步骤 | 操作 | 说明 |
|------|------|------|
| ① 定位幻觉场景 | 按问题类型/工具类型切分抽评幻觉率 | 找出集中触发场景 |
| ② 检查上下文处理 | 长路径查询是否被截断后 LLM 自行补全 | 排查 RAG/工具返回截断逻辑 |
| ③ 加约束 | 在 Prompt 中强制"未查询到必须说明，禁止补全"；限制最大路径长度 | 规则约束 + Prompt 迭代 |
| ④ 临时处置 | 幻觉率 > 5% 期间，自动报告转人工复核 | 立即生效 |
| ⑤ 回归测试 | 修复后跑一轮 LLM 质量回归（30 条抽评） | 闭环验证 |

### 2.9 人工审核业务效果监控

链鉴 AML 的预警最终要由**合规审核人员**确认、驳回或补充调查。审核行为既是最直接的预警质量反馈，也反映系统对业务的实际价值。

#### 监控内容与阈值

| 指标 | 正常范围 | 告警级别 | 含义 |
|------|---------|---------|------|
| 每日预警量 | 环比 ≤ ±30% | 🟢 | 预警量稳定 |
| 高风险预警占比 | 环比 ≤ ±30% | 🟢 | 风险等级结构稳定 |
| **待审核积压量** | < 1 个工作日可消化 | 🟢 | 审核及时 |
| 待审核积压持续增长 | | 🟡 | 预警过多或人手不足 |
| **待审核积压 > 3 个工作日** | | **🔴** | 审核严重滞后，需扩容或降预警量 |
| 平均审核时长 | 环比 ≤ ±30% | 🟢 | 审核效率稳定 |
| 确认率 / 驳回率 / 补查率 | 见 2.5 | 🟢🟡🔴 | 预警质量反馈 |
| 审核闭环率（已审/应审） | ≥ 95%（当日） | 🟢 | 闭环及时 |

#### 反洗钱场景实际解读

**场景：待审核积压从 200 条涨到 1,500 条（红色告警）**

**合规人员看到的实际影响**：
- 平均审核时长从 4 分钟涨到 35 分钟，人手告急
- 可能是预警量暴增（模型问题）或审核耗时上升（报告质量差/Agent 答案不可信）
- **风险**：积压预警无法及时处置，高风险案件延迟调查，追溯窗口错失

**排查思路**：

| 排查方向 | 具体操作 |
|---------|---------|
| 预警量是否暴增 | 对比 2.4 风险评分 PSI、2.6 规则命中量 → 是否模型/规则/数据问题 |
| 单条审核耗时是否上升 | 抽查报告质量与 Agent 答案 → 是否 LLM 质量下降（结合 2.8） |
| 审核资源是否不足 | 与合规负责人确认人手与排班 |
| 三者皆正常 | 周期性高峰（如季末资金流动）→ 提前预警审核资源 |

## 3. 异常排查通用流程

### "六步排查法"（反洗钱版）

当任意指标触发告警时，按以下顺序排查：

```
第一步：确认是"数据问题"还是"检测问题"
  ┌─────────────────────────────────────────────┐
  │ 看缺失率报表 → 是否有字段缺失率突增？         │
  │ 看导入记录 → 是否有导入失败/重复导入？        │
  │ YES → 数据问题（走数据修复流程）              │
  │ NO  → 继续第二步                            │
  └─────────────────────────────────────────────┘

第二步：确认是"全局"还是"局部"
  ┌─────────────────────────────────────────────┐
  │ 按账户类型/交易类型/时间段/CSV 批次切片看指标  │
  │ 局部异常 → 该切片的问题                      │
  │ 全局异常 → 继续第三步                       │
  └─────────────────────────────────────────────┘

第三步：看检测输出是否变化
  ┌─────────────────────────────────────────────┐
  │ 风险评分 PSI 是否告警？预警量是否骤变？      │
  │ 规则命中量是否有单条规则异常？               │
  └─────────────────────────────────────────────┘

第四步：分析特征与图谱变化
  ┌─────────────────────────────────────────────┐
  │ 计算每个特征的 PSI 贡献度，找 Top-3 偏移特征  │
  │ 交易金额/频率/对手数/夜间占比                │
  │ 图谱：连通分量、高连通账户、路径数量         │
  │ 看这些变化是否对应已知洗钱模式               │
  └─────────────────────────────────────────────┘

第五步：检查 LLM Agent 链路
  ┌─────────────────────────────────────────────┐
  │ 工具调用成功率是否下降？推理是否正常？       │
  │ 幻觉率抽评是否超限？Prompt/上下文是否变更？  │
  └─────────────────────────────────────────────┘

第六步：生成排查结论，决定处置方案
  ┌─────────────────────────────────────────────┐
  │ ① 数据问题 → 修复数据，重新导入/跑分        │
  │ ② 客群偏移 → 判断临时/永久 → 决定迭代策略   │
  │ ③ 规则/图谱异常 → 回滚配置或重构图谱        │
  │ ④ LLM 问题 → 切换人工复核，修复 Prompt      │
  │ ⑤ 检测老化 → 启动迭代流程                   │
  │ ⑥ 业务正常 → 更新监控基准，继续观察         │
  └─────────────────────────────────────────────┘
```
